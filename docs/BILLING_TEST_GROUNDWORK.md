# Billing: test-only groundwork

31 October 2026. Owner decision: retain current limits and build test-only billing groundwork. No commercial prices, Stripe account, keys or production activation were supplied or inferred. This is not a deployed payment system.

## Access and data boundaries

The three-hour trial, two free active lists and five manually paid/complimentary active lists remain governed by the existing account/list services. Account suspension still overrides access. No billing event writes `UserAccount.IsPaid`, creates duplicate entitlements, deletes lists or grants MCP scopes. The calculated test subscription preview never applies to account access. Billing status, account status and actual entitlement are separate.

`BillingCustomers` maps an account to a unique test customer and a minimal reconciled JSON ledger containing subscription/invoice/payment IDs, statuses, periods, amounts, refunds and safe hosted invoice links. `BillingWebhookEvents` records event ID, customer ID, allowlisted type, processing/retry status and timestamps. `BillingCheckoutAttempts` durably fences account/request/plan retries. No raw webhook, card number, payment-method details, email, address or provider exception payload is stored. Account foreign keys restrict deletion pending the approved support review; do not apply diagnostics' 30-day retention to billing history without a retention decision.

`20261031061702_AddTestBillingLedger` is additive. Its rollback takes locks and refuses to remove nonempty billing history. Rehearsals use generated local schemas only. Production migrations remain unapproved.

## Disabled configuration and safe sandbox setup

Checked-in `Billing.Enabled=false`. Enabling is permitted only in ASP.NET `Development`; production/test-key substitution cannot bypass that environment gate. Nonempty keys must be `sk_test_…` and webhook secrets `whsec_…`. Live-mode webhook objects and remote records are rejected. This release contains no switch to activate live payments or paid entitlements.

After an owner supplies a dedicated Stripe sandbox, put secrets in the existing private local configuration/secret store, never the repository. Configure `Billing.SecretKey`, `WebhookSecret`, `MonthlyPriceId`, `AnnualPriceId` and `WebsiteOrigin`. The origin must be HTTPS (HTTP only for loopback), with no credentials/path/query/fragment. Prices are server-owned IDs; Checkout validates active, test-mode AUD monthly/yearly recurrence. No price amount was invented or published. The billing UI remains unavailable when required configuration is absent. Creating a provider account, publishing a webhook tunnel or spending money is not part of this work.

The official Stripe.net **53.1.0** adapter creates hosted subscription Checkout and customer-portal sessions. Card entry stays on Stripe. Fixed return URLs point to `/account/billing`; only Stripe's expected HTTPS hosted origins are accepted. Browser APIs require an authenticated first-party cookie, existing request protection, expected account ID and rate limits. MCP/device credentials cannot use them. No arbitrary customer, price or return URL is accepted from the customer.

Checkout uses a durable UUID/plan fence before the remote request, provider idempotency and an account advisory lock. Retries reuse the same request; changed plans/expired requests conflict. A different request is blocked for 24 hours, even if the first checkout was abandoned, to avoid duplicate subscriptions during response loss. This intentionally conservative test restriction is explained by the API. A current nonterminal subscription directs the customer to the portal. A lost customer-creation response can leave an orphan test customer; review sandbox orphans before any future release. Customer creation alone never starts a subscription. Return query parameters are informational and never payment confirmation.

## Webhooks and reconciliation

`POST /billing/stripe-webhook` is outside the browser-cookie API prefix and uses raw-body SDK signature verification instead. Requests are bounded to 128 KiB. Timestamp tolerance is five minutes in either direction. Known snapshot-style event types are explicitly allowlisted: Checkout completion/expiry, subscription creation/update/deletion, invoice paid/payment-failed/voided/finalized and charge refunded. Unsupported verified types are acknowledged without storage. Thin-event payloads are not supported by this release; configure a matching snapshot destination when sandbox verification is eventually authorised.

An event is acknowledged only after its unique ID is durable. Concurrent duplicates cannot create another receipt. A minute worker serializes reconciliation per customer and reads **current provider state**, not stale event subscription fields. Scheduled hourly refreshes recover missed events. Provider failures retain the last good snapshot and pending receipt with increasing retry delay up to an hour. Unknown customer IDs are `unmatched` for support review; metadata cannot attach them to another account. No raw exception text is returned. Rate limiting can return 429; the provider must retry.

Provider timeouts can surface as cancellation exceptions even when the request itself was not cancelled. These are retryable outages and now persist the backoff/attempt count. Genuine caller/host cancellation still propagates and rolls back the processing attempt. The final timeout/cancellation acceptance case verifies both paths and successful recovery.

The adapter fetches all subscription statuses, invoices and charges in pages of 100 with a hard 1,000-record cap per resource. Truncated, live, malformed or mismatched histories fail reconciliation rather than replacing good data. More complex histories require manual review. Refunds are the provider's accumulated charge-refunded amounts, including partial refunds. Payments use captured amounts, excluding uncaptured authorizations. Invoice paid amounts and charge payments are separate views and must not be added together as revenue. Credits, disputes, fees, tax recognition, multi-currency accounting and partial-payment allocation are not an accounting ledger.

Subscription item period ends are shown as **billing periods**, not promised paid-through access. A cancellation scheduled before period end remains visible. A refund does not imply a Stripe subscription cancellation or a local entitlement change. Future grace periods, refund entitlement rules, tax, paid-through computation and downgrade policy need commercial decisions and separate implementation before production.

## UI, reporting and support

Settings links to `/account/billing`; private metadata excludes indexing. Customers see current real access, test-only status, reconciliation time, subscription periods/cancellations, invoices/receipts and captured/refunded amounts. Missing configuration, request failure, loading, retry and account change have explicit states. Private data clears on account change; retries retain the same checkout UUID. `/superadmin/billing` uses the existing server-side admin guard and protected API.

Admin MRR is an **estimate from the latest test snapshots**, capped at the first 1,000 customers and labelled when partial: active subscriptions whose period has not ended, annual cents divided by 12 with fractional cents truncated. Scheduled cancellations remain included until end; trials, failed subscriptions and manually complimentary accounts are excluded. Cancellation/failed counts are current subscription counts, not cohort churn or recognised revenue. Pending/unmatched totals expose reconciliation problems. No real revenue, churn rate or collection success is claimed.

Read-only support export now includes billing records and webhook receipts through the account's customer mapping. Hosted links and exports are private; verify ownership and secure delivery, review nested snapshot coverage and external-provider records. Deletion remains support-reviewed. Disable billing to stop new provider actions; preserve records and repair/reconcile rather than forcing a destructive rollback.
