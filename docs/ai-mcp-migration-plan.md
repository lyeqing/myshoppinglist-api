Implementation refinements: jobs are immutable account-owned batches, independent of lists so list deletion cannot erase unresolved research; selection/refresh check list ownership afresh. Candidate evidence retains typed tissue/matching facts without another canonical catalogue or attribute framework. The existing receipt result adds an optional job ID instead of a second replay engine. No price-verification columns were needed because AI reports never enter eligible current/history price tables. Source resolution explicitly preserves existing metadata for research while retaining browser callers' enrichment behaviour.

Complexity increased for the cohesive research lifecycle/contracts/UI and decreased for dead bindings/test code and stale guidance. No new dependency, project, repository layer or price engine was introduced. No remote PR was created: the GitHub CLI is unavailable. Work remains local on backend `codex/ai-mcp-migration-audit` and frontend `codex/ai-mcp-research`.

Not completed: independent promotion of AI prices into verified observations/totals; cross-user caching; inactive-product scheduling; durable executor claims; a complete issue-event timeline or automatic evidence purge; production migration/activation; live retailer permission/access testing; commercial-client certification; legacy-extension retirement. Issue acknowledgement never verifies a price. Evidence is retained with the account, and existing export discovers the new account-owned tables. These are explicit limits, not simulated successes.

## Scope and conclusion

Reviewed the tracked backend and adjacent `D:/pra/myshoppinglist` frontend/extension inventories, application entry points, models/configurations/migrations, principal services, MCP adapters, security documentation and test infrastructure. This is a source/schema review and local regression baseline, not a production database audit, live retailer test or commercial AI-client certification. Backend baseline commit: `586bd9e`; both working trees were initially clean. Work is on `codex/ai-mcp-migration-audit`.

The existing modular monolith is suitable. Retain the ASP.NET Core application, PostgreSQL database and Next.js website. Reuse identity, lists, private products, retailer mappings, price history, matching, comparison arithmetic and the existing OAuth MCP host. No replacement server, microservice, paid AI API or provider abstraction is needed. A percentage of reusable code would be misleading: the principal domains already exist, while the external AI evidence/review workflow does not.

The brief changes the extension-first direction in [the older work plan](MYSHOPPINGLIST_CODEX_WORK_PLAN.md). External customer-initiated AI research is the primary intended executor; account privacy and the prohibition on cross-user browser execution remain. The initial audit added only the two plans; later authorized implementation is recorded above. Inventory/gap statements below describe that initial snapshot.

## Smallest maintainable target

Customer AI → existing scoped OAuth `/mcp` → thin adapters → existing domain services plus a small research service → existing PostgreSQL database. Website → existing authenticated gateway/API → the same research service. External search runs in the customer's AI application. Optional browser capture remains a separate evidence source. A server cannot start or commandeer a customer's personal AI session.

Keep `Mcp/` for transport and protocol errors, `Contracts/` for bounded inputs/results, `Services/` for research lifecycle/validation, and existing `Models/` and EF configurations for persistence. Do not create a new project per logical module. Extract a small shared validator only where two real callers need it; preserve existing transaction and lock ordering.

### Proposed data changes, not generated migrations

Retain `Product`, `ShopProduct`, current prices/history, observations, current lists and mutation receipts. Add only the following durable research concepts:

| Change | Minimum data and integrity requirements |
| --- | --- |
| `ResearchJob` | Account, originating connection reference where applicable, optional owned list, intent/requirements snapshot, workflow version, status, revision, timestamps and retry/backoff. Account-bound UUID plus input hash rejects changed retries. A job is also the batch; no separate batch table initially. |
| `ResearchCandidate` | Job/account, client candidate key, retailer/product URL/code, bounded structured identity/evidence, reported price/currency/scope/location/promotion, observed/received dates, deterministic validation outcome, match basis, separate AI confidence and optional promoted product/mapping. Evidence immutable after submission; corrections append a new candidate. Enforce unique `(job, candidateKey)` and payload replay checks. |
| `ResearchIssue` | Job/account, optional candidate or owned mapping, stable code, safe detail, required next action, status, revision and resolution basis/timestamps. Dedupe open issues by affected target/code. Permission failures before an owned job is established return errors rather than creating inaccessible jobs. |
| Existing provenance/prices | Link promoted observations to research evidence through an optional FK on `ContributionObservation`; retain its existing history linkage. Add an explicit AI source category and verification status where persisted price readers need it. Existing rows default to legacy/unknown evidence status, never retroactively verified. Update provenance constraints and readers together. Keep unrelated extension metadata optional for AI provenance. |
| Product characteristics/relationships | Add nullable typed tissue attributes only after fixture validation proves what must be durable. Retain submitted attributes in candidate evidence first. Use current exact matcher/package-family logic. Private relationship proposals can reference another owned product in candidate evidence; extend the existing relationship model only when durable private review is required. Do not introduce another canonical catalogue or general attribute framework. |

“Accepted” means the submission passed validation, not independently verified retail truth. AI confidence, a plausible URL, customer selection or a recent search does not verify a price. Preserve unverified reported values in evidence/review, visibly labelled and excluded from definitive totals. Promotion into eligible current prices requires an explicit evidence policy and checks; an unsupported report must not overwrite a previously observed price or advance its checked/verified timestamp. Product selection can succeed without a usable price.

Use composite ownership keys/FKs for job/candidate/issue/list/product links, unique idempotency keys, bounded numeric/text payloads and UTC timestamps. Check location belongs to retailer. Keep current-price scope/currency uniqueness and history indexes. Add only indexes serving account job/review and refresh queries. Proposed initial limits: 20 candidates per submission within the existing 64 KiB MCP bound, pages at most 50, and bounded evidence excerpts instead of entire pages. Reject oversized batches explicitly; never truncate silently.

Generate additive EF migrations in a later phase, rehearse on representative disposable PostgreSQL data and fingerprint existing rows. Back up and verify the exact target before any real upgrade. Retain populated evidence/receipts on rollback: disable new entry points and roll forward, or use a separately reviewed recovery; do not drop history to downgrade. Retention must bound raw evidence without deleting unresolved issues, required provenance or retry receipts. Extend account export/deletion tooling and document retention before release. No production database was inspected or migrated here.

## Research workflow and acceptance

Maintain one versioned workflow source reused by concise server instructions, `get_research_instructions`, tool descriptions, a reusable MCP prompt and the website's prepared request. Prompt discovery is optional client functionality; the tool is the portable fallback. Instructions are guidance, never authorization.

1. Capture exact/brand-specific/flexible intent, quantity, pack/variant requirements and allowed alternatives. Read instructions/context and search owned saved products before external research.
2. Research only relevant enabled retailers using the client's available search/browsing. Record missing access, missing price and unknown stock separately. Never bypass retailer challenges or infer stock from a failed search.
3. Submit source URLs, bounded factual evidence, actual observation times and limitations. Validate URL/product/retailer identity, GTIN contradictions, dimensions/units, currency, dates, promotion bounds, duplicate payloads and suspicious price changes. Quarantine anomalies for review; AI arithmetic/confidence is not authoritative.
4. Present three to five relevant candidates where available, distinguishing exact products, different packs and alternative brands. Show source/date/scope, unknowns and deterministic comparable unit prices only when evidence supports them.
5. For “Add Kleenex toilet tissue”, retain Kleenex intent and ask the customer to choose range/pack when ambiguous. Compare sheets/rolls/ply/dimensions only when known; roll count alone cannot establish value. Conflicting barcodes/variants block exact matching. A blocked Coles page becomes an issue, never a fabricated price.
6. Save only the selected candidate through the existing authorized list operation. Explicit exact-product instructions may suffice without an extra product confirmation, subject to client controls. Confirm success only after a durable server result; a lost response retries unchanged.
7. Display remaining issues on website/MCP. Partial batches retain successes and rejected/unfinished entries. An unsuccessful search leaves previous evidence dates intact. Cancel stops future work and retains committed outcomes with honest state.

Refresh policy should be configured server-side: propose a 24-hour active-list target, promotion boundaries, 3–7-day inactive targets and failed-attempt backoff. These are refresh targets, not live-price promises. Dedupe by account/product/retailer/location/scope and policy window; unchanged retries do not duplicate observations. Keep current weekly rules until explicitly migrated with regression coverage. A future executor can consume these same contracts; no paid backend worker is proposed now.

## Risks and unresolved release decisions

- Evidence policy: define which source evidence may support an observed price, what requires review and how suspicious changes are quarantined. Conservative proposed default is reported/unverified, excluded from definitive savings. Customer selection is authorization, not price verification.
- Compatibility: verify actual target plans, public endpoint, callbacks and OpenIddict metadata. Current preregistered public-client support is promising but not a tested commercial integration. Add CIMD/DCR only if the selected target requires it.
- Data/retention: preserve account-private products and receipts; decide bounded evidence retention/export/deletion and private relationship review. No shared cache or cross-user research is proposed. Existing retailer-policy review in [the community decision](COMMUNITY_DATA_DECISION.md) is background evidence, not newly obtained permission.
